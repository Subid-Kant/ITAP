# ITAP curated training data

This folder is generated by `../generate_itap_curated_dataset.py`. It contains three separate JSONL datasets because ITAP has three different learning problems. Do not merge them into one training file.

| File | ITAP use | Unit of learning | Target |
|---|---|---|---|
| `itap_llama3_qlora.jsonl` | Llama 3 analyst assistant | one structured triage conversation | defensive JSON decision and recommended actions |
| `itap_lstm_exploit_sequences.jsonl` | exploit-likelihood predictor | six dated CVE feature observations | exploit observed within 72 hours / probability |
| `itap_autoencoder_network_flows.jsonl` | network anomaly detector | one normalized network flow | reconstruction of benign flows; labels are evaluation-only |

## Privacy and evidence rules

The included data is synthetic, deterministic seed data. It demonstrates the ITAP schema and lets Kaggle notebooks run end-to-end, but it is not sufficient to claim detection accuracy or production readiness. Replace/augment it with de-identified, authorized telemetry. Never include passwords, JWTs, API keys, raw personal names, email bodies, full URLs containing tokens, or real public IP addresses without an approved retention policy. Use stable pseudonymous IDs such as `asset-042` and `src-119`; keep the lookup mapping outside Kaggle.

## Recommended production collection

1. Export one immutable JSON event per scan, flow, alert, incident update, and remediation outcome. Add `schema_version`, UTC timestamp, source system, collector version, a consent/authorization tag, and a label provenance field.
2. Join only by pseudonymous asset, incident, and source identifiers. Use time-based train/validation/test splits so later events never leak into earlier predictions.
3. Human analysts must label confirmed exploitation, benign false positives, incident status, MITRE mapping, and remediation outcome. Preserve `label_source` and `labelled_at`.
4. For the autoencoder, train only on a reviewed benign baseline. Keep attacks out of its training partition and use labelled attacks only for calibration and evaluation.

## QLoRA ingestion

The LLM file uses a portable `messages` array. In a Kaggle TRL/Transformers notebook, load JSON, apply the Llama 3 chat template, and train only assistant tokens. Keep output validation strict: parse the generated JSON against the ITAP response schema, reject unsupported fields, and retain a retrieval layer for current CVEs/OSINT rather than trying to memorize threat intelligence in the adapter.

## Important current-project compatibility notes

* `backend/app/services/osint/osint_service.py` emits 20 OSINT features, but the bundled inference test documents a five-feature LSTM input. Version and validate a single feature contract before retraining.
* The runtime tries to load `itap_lstm_killchain_v3.h5`, `itap_lstm_waf_payloads_v3.h5`, and `itap_autoencoder_network_v3.h5`; those filenames are not present in the checked-in weights directory. Fix this deployment mismatch before relying on the models.
* The existing `itap_training_data.jsonl` repeats four scenarios. It is not a meaningful evaluation set and should not be used as the only QLoRA corpus.
